Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Student cards use WrappingFlowPane for contact details and tags. It calculates each child's wrapped height using the proposed available width, and uses the same row calculation for layout. This avoids sizing a newly created or recycled list cell using its previous width. Optional Telegram details and empty tag groups remain unmanaged, so they do not reserve layout space.

MainWindow forwards primary mouse presses on each outer list panel, including its heading and padding, to that panel's list through requestFocus(). The outer containers do not add extra Tab stops. ReadOnlyListView handles arrow, page and Home/End scrolling independently of row selection; normal Tab and Shift+Tab traversal remains available.

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object). A Person is uniquely identified by its StudentNumber: two persons are the same (Person#isSamePerson()) if they share a student number. In addition, each Email and (if provided) Telegram username must be unique across all persons.
  • stores all AcademicClass objects in a UniqueAcademicClassList. Each class is identified by its ModuleCode and ClassName and references its assigned students as Person objects. Students can belong to multiple classes.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • exposes the academic classes selected by the current filter as an unmodifiable ObservableList<AcademicClass> for the UI to observe.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Listing students by class

The listbyclass command displays students assigned to the class at a one-based index in the currently displayed class list, not necessarily the full stored class list. It optionally accepts a positive attendance threshold and displays only class members with fewer than that many recorded attendance dates for the selected class. Students with no attendance recorded for the class have a count of zero; dates recorded for other classes do not contribute. Without a threshold, all members are displayed. It changes the student view, not the stored student records, class memberships, or the current class view.

The following sequence diagram traces listbyclass 1 t/5, assuming CS2103 (F10-2) is the first displayed class, the selected threshold is 5, and saving succeeds. It starts at LogicManager, omitting the UI caller. The input strings are defined in the diagram note. m:ModelManager is accessed through the Model interface.

  1. LogicManager passes commandText to AddressBookParser, which creates a ListByClassCommandParser and calls parse(args). The parser uses ParserUtil#parseIndex(args) for the displayed class index and, if t/THRESHOLD is present, ParserUtil#parsePositiveInteger(...) to validate the positive threshold. It creates a ListByClassCommand with the index and optional threshold.
  2. LogicManager calls execute(model) on the command. The command obtains the currently displayed classes through Model#getFilteredAcademicClassList(), checks the index against the list size, and selects the class using lastShownList.get(index.getZeroBased()).
  3. The command calls Model#filterPersonsByClassAndDisplayAttendance(academicClass, threshold). ModelManager combines the class-membership predicate with the optional threshold predicate, using attendance counts for the selected class. It also selects the class for attendance display and sorts matching students alphabetically with PersonNameComparator. Name comparison ignores case, with original spelling as a tie-breaker. The student storage order and current class view are unchanged.
  4. The command obtains the displayed student list and uses its size, the class identity, and the optional threshold to construct the success message. With t/5, it reports Listed N students taking CS2103 (F10-2) with fewer than 5 recorded attendance dates. It returns a CommandResult to LogicManager.
  5. LogicManager saves the address book before returning the result, even though this command only changes the view. The view filter itself is not persisted.

The diagram summarises index and threshold parsing, class selection, and the combined model call. It omits model-internal filtering and refresh calls, logging (including its extra student-list access), list-size and class-field access, message formatting, and storage calls to keep the successful path readable.

Other outcomes: Missing, non-integer, zero, negative, or overflowing indices cause a ParseException before command creation. A malformed, zero, negative, or overflowing threshold is also rejected before command execution. A positive index beyond the displayed class list (including when that list is empty) causes a CommandException before the student filter or attendance display changes. A valid class with no matching students succeeds: the student view becomes empty and the result reports zero students. If saving fails after filtering, LogicManager reports a CommandException; the already-updated view is not rolled back.

Recording and removing attendance

The addattendance STUDENT_INDEX CLASS_INDEX d/YYYY-MM-DD and deleteattendance STUDENT_INDEX CLASS_INDEX d/YYYY-MM-DD commands update one attended date for a student-class pair. Both indices refer to the current displayed lists, which may be filtered independently. They are resolved when the command executes, rather than against the full stored lists during parsing.

Attendance represents the association between a Person and an AcademicClass. It stores unique attended dates in a TreeSet<LocalDate> and derives the attendance count from the set size. AddressBook owns the records and resolves their endpoints to stored students and classes. Membership eligibility is command policy: additions require the student to be assigned to the class, but removals can correct retained history after unassignment.

Recording a date

The following success path uses addattendance 1 2 d/2024-02-29. The selected student is assigned to the selected class, the date is not in the future, and it has not already been recorded for that pair.

Open the recording diagram at full size.

  1. LogicManager calls AddressBookParser#parseCommand(commandText), which delegates to AddAttendanceCommandParser#parse(args). AttendanceParserUtil#parseArguments rejects unknown or duplicate prefixes and requires d/. ParserUtil#parseIndices parses exactly two positive indices; ParserUtil#parseAttendanceDate validates the calendar date. The parser creates an AddAttendanceCommand.
  2. The command obtains Model#getFilteredPersonList(), validates the student index and selects the student. It then obtains Model#getFilteredAcademicClassList(), validates the class index and selects the class. It checks membership before attempting to record attendance.
  3. The command calls Model#addAttendance(person, academicClass, date). ModelManager delegates to AddressBook, which reuses the pair's record or creates one if none exists. Attendance#addDate rejects future dates using the computer's local calendar date and returns whether the date was newly added.
  4. On success, ModelManager#refreshFilteredPersonList() re-evaluates the existing predicate and recomputes attendance counts when a class threshold is active. Filters and ordering are retained, but students who reach the threshold disappear and displayed indices may shift. The UI observes the list and refreshes its cards.
  5. The command returns a success CommandResult. LogicManager updates command history and saves the address book through Storage before returning the result.

Removing a date

The following success path uses deleteattendance 1 2 d/2024-02-29. The date is already recorded for the selected student-class pair. The student and class still exist, but current membership is not required.

Open the removal diagram at full size.

  1. DeleteAttendanceCommandParser uses the same argument, index and date parsing helpers, then creates a DeleteAttendanceCommand. The command validates and resolves the displayed student and class indices in that order.
  2. The command calls Model#removeAttendance(person, academicClass, date) without a membership check. ModelManager delegates to AddressBook, which resolves stored endpoints and locates their attendance record. Attendance#removeDate removes only the specified date and returns whether it existed.
  3. A successful removal triggers the same student-view refresh as an addition. Other histories and memberships are unchanged. Removing the last date leaves a zero count; it does not delete the student or class.
  4. The command returns a success CommandResult, and LogicManager updates command history and saves the address book.

Both diagrams follow the existing Logic/Model colours and start at LogicManager, omitting the UI caller. The constructor arguments denote the parsed student index, class index and date. Parser helpers, list indexing, membership inspection, private command helpers, model internals, logging, history and storage calls are summarised in notes rather than shown as additional lifelines. ModelManager is accessed through the Model interface.

Validation, persistence and lifecycle

  • Invalid argument structure, non-positive or overflowing indices, and malformed or impossible dates cause a ParseException before command creation. Date syntax uses years 0001 to 9999; future-date eligibility is checked by the model during execution, not by the parser.
  • An index beyond its displayed list, including an empty list, causes a CommandException before mutation. Adding attendance for an unassigned student also fails before mutation.
  • A duplicate addition or an absent date on removal returns false from the model; the command converts it into a CommandException. Model IllegalArgumentExceptions, including future-date errors, are also converted into command failures. Rejected operations do not change attendance.
  • Previously recorded dates remain removable after a clock rollback or timezone change, even if they now appear to be in the future. An unrecorded future date is rejected. Storage restores history through Attendance#fromRecordedDates without applying today's date as a new-entry restriction.
  • JsonAdaptedAttendance and JsonSerializableAddressBook persist the association and dates. Student and class edits preserve history by rebinding the association; unassignment retains it, while deletion of either endpoint removes the associated records. Reassignment can reuse retained history.
  • If saving fails after a successful command mutation, LogicManager reports a CommandException and restores the previous command history. The attendance mutation and refreshed view are not rolled back in memory.

The parser and command tests cover invalid input and duplicate/missing dates. AttendanceIndexTest covers independently filtered panels and displayed bounds, while AttendanceLifecycleTest covers edits, deletion, unassignment/reassignment, clock-related history handling and save/reload.

Arrow key command history navigation

Arrow key navigation lets users recall previously executed commands without executing them again. CommandBox delegates history storage and navigation to its CommandHistory, which holds two separate lists and tracks the draft and the current browsing position.

Up moves towards older entries and Down moves towards the draft (newer entries). Navigation stops at either boundary, and empty history leaves the input unchanged. Modified arrow keys (such as Shift+Up or Ctrl+Down) do not trigger history navigation. AddressBook stores the latest 20 successful command strings, serialized as commandHistory in the existing JSON file. LogicManager appends each successful command before saving and restores the previous history if saving fails. History survives clear and application restarts. Older JSON files without this field load with empty history. MainWindow seeds CommandBox through Logic.getCommandHistory() on startup; drafts, browsing positions and temporary edits remain in memory only.

Field Purpose
commands Stores up to 20 successful commands in execution order, oldest first. Editing past commands does not change these entries.
workingCommands Holds a working copy of the history. Temporary edits remain available until the next non-blank command submission, whether it succeeds or fails.
draft Preserves the input from before the user started browsing history. Moving Down past the newest entry restores it. It is separate from the lists because it has not been successfully executed.
position Identifies the selected entry in workingCommands, using a zero-based index. A value equal to the list size represents the draft.

In the diagram, position = 2 selects list. With four history entries, position 4 represents the draft. Moving Down past find Alice restores addclass m/CS2103 n/f.

Preserving temporary edits with two command lists

commands preserves the successfully executed commands. workingCommands is a separate list that preserves temporary edits while browsing history. These partial object diagrams show only the two lists, with entries numbered from zero.

Step 1: Recall. After executing help, find Carol, list, and find Alice, the user presses Up to recall find Alice. Both lists contain the same commands.

Step 2: Edit and navigate away. The user changes the input to find Bob without executing it, then presses Up to recall list. Before moving, saveCurrentInput() saves find Bob in workingCommands. The original list still contains find Alice.

Pressing Down now recalls find Bob, so the user can continue editing it. Using a single list would either overwrite the original history entry or lose the temporary edit. After a successful or failed submission, resetNavigation() rebuilds workingCommands from commands, discarding temporary browsing edits.

A successful submission first adds the command to commands and clears the draft. A failed submission preserves the failed input as the draft without adding it to history. Both cases reset position to the draft position.

Adding an academic class

Implementation

The addclass command creates an empty AcademicClass, identified by its ModuleCode and ClassName. AddressBook stores academic classes in a UniqueAcademicClassList, which rejects duplicate module code and class name pairs.

Given below is an example usage scenario for addclass m/CS2103 c/F10-2, assuming the class does not already exist.

Step 1. The user enters addclass m/CS2103 c/F10-2. LogicManager passes this command text to AddressBookParser, which creates an AddClassCommandParser.

Step 2. The command parser checks the arguments and uses ParserUtil to construct the ModuleCode and ClassName. It creates an empty AcademicClass and wraps it in an AddClassCommand.

Step 3. LogicManager executes the command. The command calls Model#hasAcademicClass() to check for an existing class with the same identity, then calls Model#addAcademicClass() when the class is absent.

The following sequence diagram shows how this operation goes through the Logic component. commandText is "addclass m/CS2103 c/F10-2", arguments is " m/CS2103 c/F10-2", and a is the class created by the command parser. The parsing helper calls, creation of a, and construction of the CommandResult are omitted for clarity.

Step 4. ModelManager delegates the addition to AddressBook. AddressBook copies the current academic class list, appends the new class, and passes the updated list to UniqueAcademicClassList#setAcademicClasses(). It then registers the class as a student observer so its membership can track student updates.

Similarly, the model sequence diagram below expands the addAcademicClass(a) call from the logic diagram:

Step 5. The command returns a successful CommandResult with the message New class added: CS2103-F10-2. LogicManager saves the updated address book through Storage before returning the result to the UI. Storage calls are omitted from the logic diagram.

Note: The logic diagram shows both successful addition and duplicate-class rejection. The model diagram expands only the successful addition. Invalid arguments cause a ParseException before the command is created. If Model#hasAcademicClass() returns true, the command throws a CommandException without adding the class. Neither failure reaches the save operation.

Deleting an academic class

The deleteclass command identifies an existing class by its one-based index in the currently displayed class list. AddressBookParser delegates argument validation to DeleteClassCommandParser, which uses ParserUtil.parseIndex() and creates a DeleteClassCommand containing an Index. At execution time, the command retrieves Model#getFilteredAcademicClassList(), checks the index against its size, and calls Model#deleteAcademicClass() with the selected stored class. This is the same observable list used by the class panel, so selection respects the current class filter and display order. Invalid indices are rejected without changing the model.

The following diagram shows a successful run of deleteclass 1, assuming at least one class is displayed. The first displayed class is removed and the returned feedback identifies the deleted class. The existing model deletion path removes its assignments and attendance records while retaining student records. Remaining displayed classes are renumbered automatically. Parsing helpers and result construction are omitted for clarity; LogicManager saves the updated address book before returning the result to the UI. No storage schema or model interface change is required for index-based selection.

Invalid arguments cause a ParseException before command creation. If the class is absent, the command throws a CommandException without deleting anything. These error paths are omitted from the diagram.

Assigning and unassigning students

AssignCommand and UnassignCommand change a student's membership in one academic class without adding or deleting student records or classes. AssignCommand and UnassignCommand accept student and class indices in their respective displayed lists, with the student index first. Hidden records cannot be selected.

For example, assign 1 2 assigns an existing student to an existing class. Unassigning a student

For example, unassign 2 1 removes the second displayed student from the first displayed class. The following sequence diagram starts at LogicManager#execute(commandText), where commandText is the example above. It assumes that both records exist and the student belongs to the class. The parser validates exactly two positive indices using ParserUtil#parseIndices. The command resolves the student through Model#getFilteredPersonList() and the class through Model#getFilteredAcademicClassList(), checking each index against its displayed list size. Membership changes go through the Model interface.

  1. LogicManager asks AddressBookParser to parse the input. It creates an UnassignCommandParser, which validates the arguments and constructs an UnassignCommand.
  2. LogicManager executes the returned command, which validates both displayed indices and resolves the selected student and class.
  3. The command calls Model#unassignStudentFromClass(person, academicClass) and checks whether the model reports a successful removal.
  4. A successful removal produces a CommandResult, which LogicManager returns after saving the address book.

The Unassign membership (model) reference frame is expanded below. Only the selected class's student set changes; the student record and memberships in other classes remain intact.

If the student is not assigned to the class, AcademicClass#unassignStudent(person) returns false without changing membership. This result propagates through the model to the command, which throws a CommandException. Successful removal refreshes membership-dependent student and class filters without resetting the active filters or ordering. Indices may shift as records disappear from filtered views. Attendance history is retained for correction or reassignment.

Validation and failure paths

The activity diagram below complements the successful-execution sequence diagrams. Assignment and unassignment both resolve displayed indices and validate the selected records before updating membership and saving.

The guards distinguish successful and rejected paths. An unchanged membership means that the student is already assigned for assign, or is not assigned for unassign. In either case, the command reports an error before LogicManager reaches the saving step. A failure to save after a successful membership change is different: the in-memory change has already occurred.

Revealing affected records

Before calling Logic#execute, MainWindow captures the displayed student for assign and unassign, and the stored class position. After successful execution, it locates each target in its updated displayed list and calls PersonListPanel#scrollToStudent and AcademicClassListPanel#scrollToClass. Both methods ignore out-of-range indices, including -1 for a target that has disappeared from a membership-dependent filter. This preserves filters and ordering without revealing a replacement row. Typing and rejected commands do not scroll either panel; the reveal methods do not change keyboard focus or selection.

Validation, errors and persistence

The sequence diagrams focus on successful execution and omit individual parser validation calls, assertion lookups, formatting helpers and exception construction to keep the interactions readable.

  • Both parsers reject anything other than exactly two positive integer indices, including prefixed input. Both report ParseException before constructing the command.
  • Both commands report an invalid displayed student or class index with CommandException, including when the relevant view is empty. Both resolve the student before the class, before attempting a membership update.
  • A duplicate assignment or an absent membership is rejected without changing memberships.
  • On successful command execution, LogicManager saves the address book before returning the result to its caller. Saving occurs outside the scope of these diagrams. If saving fails, LogicManager reports a CommandException; the in-memory membership change is not rolled back.

Appendix: Requirements

Product scope

Target user profile:

  • is a Teaching Assistant (TA) managing multiple modules and tutorial or lab groups.
  • has a need to manage a significant number of student contacts, track assignment submissions, and record attendance.
  • can type fast
  • needs to maintain clear boundaries between the different cohorts and modules they teach.
  • can type fast and prefers typing over mouse interactions to navigate the application.
  • is reasonably comfortable using Command Line Interface (CLI) apps and command shortcuts.

Value proposition: helps Teaching Assistants organise all their modules, student contacts, and assignment details in a centralized application significantly faster than a typical mouse-driven GUI app.

Non-Functional Requirements

ID Category Non-Functional Requirement
NFR01 Usability TAssist should be optimised for users who are comfortable with typing, with typed commands as the primary means of interacting with the application.
NFR02 Performance TAssist should respond to normal user commands within 2 seconds under typical usage conditions.
NFR03 Capacity TAssist should support at least 500 students across 20 classes and 10 modules while maintaining normal command response times.
NFR04 Data Persistence Every successful operation that modifies application data should be automatically saved to local storage so that the latest data remains available after the application is restarted.
NFR05 Data Integrity A failed or invalid operation should not result in partially modified or inconsistent application data. Existing valid data should remain unchanged if the operation cannot be completed successfully.
NFR06 Error Handling When an invalid command or input is entered, TAssist should provide a clear error message that identifies the problem and, where appropriate, indicates the expected command format.
NFR07 Single-User Operation TAssist should operate as a single-user application and should not support multiple users accessing the same application data during normal operation.
NFR08 Data Storage TAssist data should be stored locally in a human-editable text file and should not rely on a database management system.
NFR09 Platform Compatibility TAssist should work on Windows, Linux, and macOS without relying on operating-system-specific functionality.
NFR10 Runtime Compatibility TAssist should be compatible with Java 25.
NFR11 Portability TAssist should run without requiring an installer and should be distributed as a single JAR file, or a single ZIP file if additional files are unavoidable.
NFR12 Offline Availability Core TAssist functionality should not depend on the team's own remote server and should remain usable without an Internet connection.
NFR13 Display Compatibility The GUI should work without resolution-related inconvenience at 1920×1080 or above at 100%/125% scaling, and all functionality should remain usable at 1280×720 or above at 150% scaling.

Glossary

Term Definition
TAssist The application developed to help teaching assistants manage student contacts and information across the classes they teach.
TA Teaching Assistant. The primary target user of TAssist.
Student A person whose contact and class information is managed by a TA using TAssist.
Student Number The unique institutional identifier used by TAssist to identify a student.
Module An academic course taught by the TA, identified by its module code, such as CS2103. A module may contain one or more classes.
Class A tutorial or lab group belonging to a module, identified by a class name such as F10-2. A class is uniquely identified by its combination of module and class name.
Student Profile The information stored about a student, such as their student number, name, email address, Telegram username, and class associations.
Communication Handle Contact information used to communicate with a student, such as their email address or Telegram username.
CLI Command-Line Interface. The text-based interface through which the user enters commands in TAssist.
Command A textual instruction entered into TAssist to perform an operation, such as addstudent, find, or assign.
Command Prefix A prefix used to specify a parameter in a command, such as sn/ for student number, m/ for module, or c/ for class.

Deleting and editing academic classes

Use a disposable application folder. Repeat this setup before each subsection below; clear removes all students and classes in that test copy. Enter each command separately in TAssist's command box, not in the terminal or as a single pasted block.

clear
add sn/A0999701X n/Alice Manual e/alice.manual@example.com
add sn/A0999702Y n/Bob Manual e/bob.manual@example.com
addclass m/CS2103T c/F01
addclass m/ST2334 c/T24
assign 1 1
assign 1 2
assign 2 2
addattendance 1 1 d/2020-01-01
addattendance 2 2 d/2020-01-02

Deleting a class: deleteclass

  1. Try deleteclass, deleteclass 0, deleteclass abc, deleteclass 1 extra, and deleteclass 999. Expected: format or invalid-index errors; both classes, memberships and attendance remain unchanged.
  2. Run listbystudent 2, then deleteclass 1. Expected: the displayed ST2334-T24 class is deleted, even though it was class 2 in the full list. The filtered Classes panel becomes empty.
  3. Run list and listclass. Expected: both student records remain; CS2103T-F01 is now class 1. Run listbyclass 1: Alice remains assigned with attendance 2020-01-01. In data/addressbook.json, the classes and attendance arrays must contain no ST2334-T24 records.
  4. Run list, listbystudent 2, then deleteclass 1. Expected: an invalid-index error for the empty class list. Run listclass, close the window and reopen the same JAR. The deleted class stays absent; both students and the surviving class remain.

Editing a class: editclass

  1. Repeat the setup. Try editclass, editclass 0 c/F02, editclass 999 c/F02, editclass 1, editclass 1 m/123, and editclass 1 c/---. Expected: format, index, missing-field or validation errors; neither class changes.
  2. Try editclass 1 m/ST2334 c/T24. Expected: a duplicate-class error; the original identities, memberships and attendance remain unchanged.
  3. Run listbystudent 2, then editclass 1 c/T25 and editclass 1 m/ST2334A. Expected: only the supplied field changes each time; the class becomes ST2334A-T25. Run editclass 1 m/CS2101 c/L01: both fields change, and Bob's class filter stays active.
  4. Run listclass, then listbyclass 2. Expected: CS2101-L01 contains Alice and Bob; Bob retains attendance 2020-01-02. Close the window and reopen the same JAR. The edited class, memberships and attendance persist; CS2103T-F01 remains unchanged.
  5. In this disposable copy, run clear, then editclass 1 c/F02. Expected: an invalid-index error for the empty class list; no class is created.

Persistent command history

  1. Start another disposable copy in a fresh folder. Before submitting any commands, focus the empty command box and press Up and Down. Expected: the input stays blank and no error appears. Then submit list, find HistoryNoMatch, and listclass, then submit the invalid command notacommand. Close using the window's close button, rather than the exit command, so shutdown adds no history entry.
  2. Reopen the same JAR and focus the command box. Press Up repeatedly. Expected: listclass, find HistoryNoMatch, then list; further Up presses stay at list. The failed command is absent. Recalling commands does not execute them or change the feedback. Press Down until the input is blank; further Down presses keep it blank.
  3. Type unfinished draft without submitting it. Press Up, replace the recalled listclass with list without submitting, then press Up and Down. Expected: the temporary edit list returns. Press Down again: unfinished draft returns. Close using the window button and reopen the same JAR. Expected: the input starts blank and Up recalls the original listclass; temporary edits and drafts are not saved.
  4. Press Down until the input is blank. Press Up to recall listclass, then press Enter. Expected: the command executes successfully and the input clears. Close using the window button and reopen the same JAR. Press Up twice: both newest entries must be listclass, confirming that the recalled execution was saved as another entry. Press Down until the input is blank.
  5. Submit 21 separate commands, find History01 through find History21, then close using the window button and reopen. Expected: Up recalls find History21 back through find History02 only; further Up presses stay at find History02. Only the latest 20 successful commands are retained.

Assigning a student to a class

    2. Test case: assign 1 1
      Expected: Success feedback identifies Alice and the class; its count becomes 1.
    3. Test case: find Bob, then assign 1 1
      Expected: Bob is assigned using his displayed index; the count becomes 2 and the search stays active.

  2. Duplicate assignment and errors

List-panel feedback and student-card layout

Use a disposable application folder for these checks.

Revealing records after assignment and unassignment

  1. Prepare at least 30 students and 25 classes. Run list and listclass. Check that student 30 has no class memberships and class 25 has no students.
  2. Scroll both panels to the top so student 30 and class 25 are off-screen. Run assign 30 25. Expected: both targets come into view, class 25 shows one student, and the command box keeps focus.
  3. Scroll both panels back to the top, then run unassign 30 25. Expected: both targets come into view and class 25 shows zero students.
  4. Scroll back to the top and repeat unassign 30 25. Expected: a not-assigned error, unchanged membership, and no command-triggered scrolling. Typing assign 30 25 without submitting it must also leave both panels in place.
  5. Submit assign 30 25, then run listbyclass 25, listbystudent 1, and unassign 1 1. Expected: both filtered panels become empty. Neither filter resets or reveals an unrelated record. Run list and listclass to restore the full lists.

Repeated scrolling with changing card heights

  1. Prepare enough students to scroll through several screens. Include short and long names, emails and tags, students with and without Telegram usernames, and students with no tags. Use distinct Telegram usernames so misplaced details can be identified.
  2. Make the Students panel narrow, scroll repeatedly from the top to the middle and bottom, then widen the panel and repeat. Also resize while positioned in the middle. Expected: each card retains its own details; contact details, tags and adjacent cards do not overlap.
  3. Find one student using a unique name keyword. Run edit 1 tg/ t/, then list and scroll away and back. Expected: the edited student's Telegram username and tags disappear without leaving an empty tag row or showing another student's details.
  4. Find the same student again. Restore optional fields using an unused valid username, for example edit 1 tg/layout_probe_unique t/tutorial t/ThisIsAVeryLongTagThatMustWrapInsideTheStudentCard. Run list and repeat scrolling and resizing. Expected: the username and tags reappear and wrap within that student's card.
  5. Repeat the scrolling checks after listbyclass CLASS_INDEX, replacing CLASS_INDEX with a displayed class containing enough assigned students to scroll. Include students with no attendance dates and students with enough dates to wrap over several lines. Expected: attendance remains below the contact details and tags, inside the correct card.
  6. Click a panel heading or background, or use Tab/Shift+Tab to focus its list, then press Up/Down. Expected: only the focused list scrolls; records remain unselected and unchanged.
